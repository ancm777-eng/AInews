## 항목 2 — Inherent Faraday 과학 에이전트

### 판정: 핵심 제품·사양·벤치마크 모두 1차 자료 확인 필요

### 확인되지 않은 핵심 주장

다음은 공식 기술 문서 없이는 사실로 단정할 수 없습니다.

- Faraday의 정확한 파라미터 수가 27B인지
- 기반 모델이 정확히 `Qwen 3.6`인지
- Edward Hughes의 공식 직책이 Chief Scientist인지
- GPT-5.5 Codex를 외부 코드 실행 모델로 사용했는지
- Claude Opus 4.8과 GPT-5.5가 실제 비교 대상이었는지
- 상용 API가 출시됐는지, 제한적 연구 프리뷰인지

특히 모델명과 버전 번호는 보도기사보다 각 공급사의 공식 모델 문서로 확인해야 합니다.

### 논리·평가 설계 문제

1. **“논문을 읽는다”와 “결과를 모른 채 blind replication한다”가 충돌합니다.**  
   출판된 논문의 전체 본문을 읽었다면 결과 섹션도 볼 수 있습니다. 실제로 결과를 가리고 methods/data만 제공했다면 그 평가 프로토콜을 명시해야 합니다.

2. **27B 모델 자체와 전체 에이전트 시스템의 성능을 혼동했습니다.**  
   Faraday가 GPT-5.5 Codex 같은 외부 모델을 호출한다면 성능은 다음의 결합 결과입니다.

   - 27B 오케스트레이터
   - 외부 코딩 모델
   - 실행 환경
   - 검색·도구 사용
   - 재시도 예산
   - 총 토큰 및 연산 비용

   따라서 “27B 모델이 GPT-5.5를 능가했다”는 결론은 동등한 도구·예산 조건의 모델 단독 비교가 아닌 이상 성립하지 않습니다. “Faraday 에이전트 시스템이 해당 평가에서 비교 시스템보다 높은 점수를 기록했다” 정도로 제한해야 합니다.

3. **“낮은 추론 비용”도 입증되지 않았습니다.**  
   작은 오케스트레이터가 대형 외부 코딩 모델을 여러 번 호출하면 총 비용과 지연시간이 오히려 커질 수 있습니다. 모델 파라미터 수만으로 시스템 비용을 판단하면 안 됩니다.

4. **“replication”의 정의가 필요합니다.**  
   코드 재실행, 결과 수치 재현, 방법론 검증, 통계적 재분석, 물리 실험 재현은 서로 다른 과제입니다. 초안은 이를 모두 “과학 논문 복제”로 묶고 있습니다.

## 항목 3 — Anthropic Mythos/Fable 데이터 보존 정책

### 판정: 가장 신뢰 위험이 높은 항목

### 명백한 내부 모순

초안은 동시에 다음 세 가지를 주장합니다.

1. 고객이 30일간 데이터를 의무 보존한다.
2. 이 데이터가 사이버 위협 분석에 사용된다.
3. Anthropic은 데이터에 전혀 접근하지 않고 중앙 서버에도 보존하지 않는다.

Anthropic이 데이터에 접근하지 않는다면 누가, 어디서, 어떤 소프트웨어로 안전 분석을 수행하는지 설명되어야 합니다. 가능한 구조는 서로 다릅니다.

- 고객 환경에서 Anthropic 제공 스캐너가 로컬 분석
- 고객이 분석 후 집계·비식별화된 신호만 전송
- Anthropic이 고객 VPC에 제한적으로 접근
- 단순 보존만 하고 사고 발생 시 고객이 제출

현재 초안은 이 중 어떤 방식인지 밝히지 않은 채 “zero vendor access”와 “mandatory threat analysis”를 동시에 단정합니다.

1. **“zero retention”과 “zero access”는 다릅니다.**

2. **HIPAA·GDPR·FINRA에 ‘aligned’됐다는 포괄적 판정은 부정확합니다.**

4. **100개 이상 고객과 Salesforce 참여는 별도 근거가 필요합니다.**  
   참여 기업 명단과 프로그램 성격이 확인되지 않으면 “including Salesforce”를 삭제해야 합니다.

5. **`Mythos-class`는 정식 제품명인지 내부 분류인지 구분해야 합니다.**  
   정식 Anthropic 명칭이 아니라 기사나 초안 작성자가 만든 분류라면 제목과 본문에서 제거해야 합니다.

### 명백한 아키텍처 오류

   이는 다음처럼 분리해야 합니다.

   - Vera CPU: NVIDIA의 Arm 기반 호스트 CPU
   - RISC-V profile/platform: NVIDIA GPU와 상호운용할 수 있는 별도 RISC-V 구현 조건 또는 소프트웨어·플랫폼 규격

2. **기존 NVIDIA GPU가 전용 x86/Arm 호스트만 요구했다는 설명은 틀렸습니다.**  
   NVIDIA GPU는 오랫동안 표준 PCIe 기반으로 여러 호스트 아키텍처와 연결돼 왔습니다. 과거에는 POWER 호스트 지원 사례도 있습니다. 문제는 “전용 ISA만 가능”이 아니라 드라이버, IOMMU, 원자 연산, 메모리 순서, 펌웨어, 부트 및 플랫폼 검증 지원 범위입니다.

3. **NVLink를 CXL·PCIe와 같은 ‘open interface standard’로 묶으면 안 됩니다.**  
   CXL과 PCIe는 산업 표준이지만 NVLink는 NVIDIA의 독자 인터커넥트입니다.

### 출처에서 확인되지 않은 기술 확장

세션 제목만으로 다음을 확정할 수 없습니다.

- PCIe Gen 6 지원
- CXL 캐시 일관성
- RISC-V와 NVIDIA GPU 간 coherent memory
- 제3자 RISC-V CPU의 NVLink 직접 연결
- 표준화된 SI 신호 제약
- reference platform specification 제공
- 패키지 수준 멀티소켓 CPU-GPU substrate
- Rubin용 맞춤형 메모리 컨트롤러 세부사항

“interoperability”는 표준 PCIe 장치 열거, 드라이버 ABI, 메모리 모델, 원자 연산, IOMMU 및 CUDA 지원 요건을 의미할 수도 있습니다. 초록이나 슬라이드에 CXL·NVLink coherence가 명시되지 않았다면 삭제해야 합니다.

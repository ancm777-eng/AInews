# 항목별 검증

## 1. NVIDIA DSX MaxLPS / Vera Rubin

### 판정: **중대한 수정 필요**

### A. Vera Rubin NVL72 표기는 공식 세대 구성과 충돌

NVIDIA가 기존에 공개한 Vera Rubin 랙 스케일 시스템의 대표 명칭은 **Vera Rubin NVL144**이며, Rubin Ultra는 **NVL576** 계열로 제시됐습니다. 초안은 Blackwell 세대의 GB200/GB300 NVL72 구성을 Vera Rubin에 그대로 적용해 다음과 같이 적었습니다.

- `Vera Rubin NVL72`
- `72 Rubin GPUs and 36 Vera CPUs`
- `Post-Rubin Ultra ... Rubin Ultra Multi-Die`이면서 NVL 수량은 생략

새로운 하위 구성인 “Vera Rubin NVL72”가 9월 15일에 별도로 발표됐다면 **그 정확한 공식 제품명과 구성표를 인용**해야 합니다. 그렇지 않다면 다음처럼 고치는 것이 안전합니다.

- **Vera Rubin NVL144**
- 144 Rubin GPU를 포함한 랙 스케일 시스템
- Rubin Ultra는 공식 명칭과 GPU 수를 별도로 확인

현재 초안의 NVL72 표기는 공개된 세대 로드맵과 명백히 충돌합니다.

### B. Hopper의 “NVL8” 표기도 부정확

로드맵 표의 다음 행도 수정해야 합니다.

> `Hopper Baseline (NVL8) | H100 / H200 SXM5`

H100/H200 8-GPU 서버의 일반적인 플랫폼 명칭은 **HGX H100/H200 8-GPU**입니다. “H100 NVL”은 별도의 PCIe 기반 듀얼-GPU 제품 명칭으로 사용됐기 때문에, `NVL8`이라고 쓰면 서로 다른 폼팩터를 혼동하게 됩니다.

권장 수정:

> `Hopper Baseline (HGX 8-GPU) | H100/H200 SXM`

### C. 기사에 근거가 명시돼야 하는 세부 주장

아래 내용은 “40% 용량 증가”에서 논리적으로 자동 도출되지 않습니다.

- PMIC와 PDU 사이의 **sub-millisecond 폐루프**
- GPU VRM의 **phase frequency를 직접 선제 조절**
- UPS 배터리와 실시간 연동
- CDU 밸브의 랙별 실시간 유량 조절
- HBM4를 포함해 접합 온도를 **75°C 이하**로 유지
- 54V와 800V가 동일 Vera Rubin 랙에서 동작하는 `54V/800V DC Hybrid`
- Annapurna Labs와의 `NVHBM` 공동개발
- d-Matrix의 `Raptor XPU`
- Lambda와 Emerald AI의 “commercial production” 검증

공식 블로그 또는 발표 자료에 이 내용이 없다면 **기술적 추론 또는 전망**으로 내려야 합니다. 특히 `NVHBM`은 표준적으로 널리 알려진 NVIDIA 제품·인터페이스 명칭이 아니므로 정확한 원문 표기가 필수입니다.

### D. “40% 더 많은 GPU”의 의미가 과도하게 확대됨

“up to 40%”가 사실이어도 다음 두 의미는 다릅니다.

1. 설치 가능한 **nameplate GPU 수**가 40% 증가
2. 실제 연산 가능한 **지속 처리용량**이 40% 증가

동적 전력 제한은 워크로드 동시성, SLA, 피크 부하 분포에 따라 추가 GPU를 설치하더라도 모든 GPU가 동시에 최대 성능으로 동작하지 못할 수 있습니다. 따라서 다음 문장은 너무 단정적입니다.

> “hyperscalers … can increase tenant GPU density by 40%”

권장 표현:

> “NVIDIA가 제시한 워크로드 및 피크 동시성 조건에서는, 동일한 시설 전력 한도 아래 설치 가능한 GPU 수를 최대 40% 늘릴 수 있다고 주장했다.”

### E. URL과 출처

`blogs.nvidia.com` 형식의 URL은 공식 도메인이지만, 다음을 페이지에서 직접 확인해야 합니다.

- 실제 제품 표기: `DSX MaxLPS`
- 약어의 정확한 풀네임
- Vera Rubin 시스템의 NVL 수
- 40%의 측정 조건
- Annapurna Labs·d-Matrix·Lambda·Emerald AI 관련 문구

“AI Infra Summit Disclosures”라는 포괄적 출처 대신 **발표 영상 타임스탬프, 슬라이드 또는 공식 보도자료 URL**을 각각 붙여야 합니다.

## 2. JAX·Transformer Engine 기반 MoE 최적화

### 판정: **핵심 수치는 내부적으로 일치하나, 시간 수정 및 벤치마크 범위 명시 필요**

### A. 시간 변환 오류

앞서 지적했듯이 정확한 시각은 다음입니다.

> **2026-09-16 00:00 KST**

다만 24시간 요건은 충족합니다.

### B. 핵심 산술은 일치

초안의 두 수치:

- 103 TFLOPS/GPU
- 1,068 TFLOPS/GPU

비율은:

> 1,068 ÷ 103 ≈ **10.37배**

따라서 반올림한 **10.4×**는 산술적으로 정확합니다.

DeepSeek-V3의 총 파라미터 수를 **671B**로 표기한 것도 알려진 모델 사양과 일치합니다.

### C. TFLOPS를 “training throughput”과 동일시하면 안 됨

TFLOPS/GPU는 연산률이고, 일반적인 학습 처리량은 다음처럼 표시됩니다.

- tokens/s
- sequences/s
- model FLOPs utilization
- time-to-train

따라서 다음 표현은 제한조건 없이 쓰면 부정확합니다.

> “10.4x throughput speedup”

출처가 실제로 TFLOPS/GPU만 제시했다면 다음처럼 써야 합니다.

> “측정된 per-GPU training compute throughput이 103에서 1,068 TFLOPS/GPU로 10.4배 향상됐다.”

실제 end-to-end 학습 시간이 10.4배 줄었다는 뜻으로 확대해서는 안 됩니다.

### D. 97% scaling efficiency에는 기준점이 필요

“1,024 GPU에서 97%”라는 값은 다음 정보 없이는 재현할 수 없습니다.

- 몇 GPU를 기준으로 한 strong/weak scaling인지
- 글로벌 배치 크기
- sequence length
- expert 수와 top-k routing
- 데이터 병렬·텐서 병렬·expert 병렬 구성
- NVLink 도메인과 InfiniBand 구성
- forward-only인지 전체 학습 step인지

`97% linear scaling efficiency` 대신 원문의 정의를 그대로 인용해야 합니다.

### E. 비교표의 중간 수치는 출처 없는 생성값

다음 값들은 본문에 근거가 없습니다.

- `Capacity-Constrained MoE: ~450–600 TFLOPS/GPU`
- `Unoptimized 1,024 GPUs: <50%`
- `Capacity-Constrained: ~75–80%`

이 값들이 NVIDIA 자료에 없다면 삭제해야 합니다. 핵심적으로 검증된 두 끝점만 비교하는 것이 안전합니다.

### F. 과장 또는 기술적 모호성

- `MXFP8 ... without precision loss`  
  → 저정밀 형식은 일반적으로 오차가 0이라는 뜻이 아닙니다. “목표 정확도를 유지하면서” 또는 “보고된 품질 손실 없이”가 적절합니다.
- `fused NCCL EP ... deduplicating tokens`  
  → 정확한 구현이 NCCL EP인지, NVSHMEM/DeepEP 계열인지, 또는 Transformer Engine 내부 프리미티브인지 원문 명칭을 따라야 합니다.
- `single-call cuBLAS Grouped GEMM`  
  → 실제 구현이 cuBLASLt인지 Transformer Engine의 custom grouped GEMM인지 확인해야 합니다.
- `lowering effective pre-training compute costs by an order of magnitude`  
  → 특정 병목 구간의 10.4배 개선이 전체 사전학습 비용 10분의 1을 의미하지는 않습니다.

### G. URL

NVIDIA Developer Blog를 1차 출처로 삼는 것은 적절합니다. 반면 Quantum Zeitgeist 등 재전재 매체는 독립 검증 출처가 아닙니다. 공식 페이지에서 표·그래프의 수치와 테스트 구성을 직접 인용하십시오.

## 4. OpenAI “Project Lily”

### 판정: **조사보도 자체와 초안의 파이프라인 추론을 분리해야 함**

### A. “raw/unredacted”와 “Privacy Filter 처리”가 서로 충돌

초안은 동시에 다음을 주장합니다.

- `raw ... conversations`
- Privacy Filter가 PII를 처리함
- 필터가 일부 식별자를 `under-redact`함
- 표에서는 Mercor가 `unredacted conversational context`를 전달한다고 함

필터가 먼저 적용되지만 일부 내용이 남는 구조라면 “raw” 또는 “unredacted”라고 일반화할 수 없습니다.

권장 표현:

> “자동 개인정보 필터를 거친 실제 사용자 대화가 검토 대상이지만, 조사보도는 일부 식별 가능 정보가 충분히 가려지지 않았다고 보도했다.”

### B. “default opt-in”은 모순적 용어

사용자가 적극적으로 선택하지 않아도 켜져 있다면 **opt-in**이 아니라 **default-on**입니다.

권장 표현:

> “소비자용 개인 워크스페이스에서 ‘Improve the model for everyone’ 설정이 기본 활성화돼 있다.”

또한 앱·지역·가입 시점·계정 유형에 따라 기본값이 다를 수 있으므로 공식 OpenAI 데이터 제어 문서와 맞춰야 합니다.

### C. 인간 평가를 곧바로 RLHF라고 단정할 수 없음

다음 단계는 서로 다릅니다.

- 모델 응답 품질 평가
- 선호 데이터 생성
- reward model 학습
- supervised fine-tuning
- RLHF/RLAIF
- 제품 품질 모니터링

계약자들이 1~7점으로 평가한다는 사실만으로 그 데이터가 실제 **RLHF reward model에 투입됐다**고 확정할 수 없습니다. 내부 문서에 학습 목적이 명시되지 않았다면 다음처럼 표현해야 합니다.

> “모델 개선 및 평가용 인간 피드백 데이터로 사용된다고 보도됐다.”

### D. “기업 확인”의 범위를 명확히 해야 함

Status에 `Corporate Confirmation`이라고 적었지만 다음 중 무엇을 OpenAI가 확인했는지 구분되어 있지 않습니다.

- Project Lily라는 코드명
- 실제 사용자 대화 사용
- 수백 명 규모
- 기억 요약 노출
- Privacy Filter의 반복적 실패
- Crossing Hurdles 및 Mercor의 역할
- 시간당 $50 초과
- RLHF 투입

OpenAI가 일반적인 인간 검토 관행만 인정했다면 Project Lily 세부사항 전체를 “기업 확인”으로 분류하면 안 됩니다.

### E. 계약·데이터 흐름을 과도하게 구체화

다음은 조사자료에 직접 적혀 있지 않으면 삭제하거나 귀속 표현을 붙여야 합니다.

- `Mercor`가 대화를 packaging하는 “Data Routing Bus”
- 계약자 데이터가 OpenAI의 `RLHF Training Datastore`로 직접 들어감
- “full conversation histories”가 모든 작업에서 제공됨
- `approximate geographic locations`가 기억 요약에 일률적으로 포함됨
- opt-out이 “past reviews”에 소급되지 않는다는 구체적 운영 규칙
- Anthropic이 “analogous workflows”를 확인했다는 문구

Mercor가 보상·계약 관리 플랫폼이라는 사실과 실제 사용자 데이터를 호스팅한다는 것은 별개의 주장입니다.

### F. 인원·보수 수치

다음 표현은 범위를 명확히 해야 합니다.

- `hundreds of contractors`
- `$50+ per hour`
- `North American contract workers`

전체 프로젝트 인원인지, 모집 공고 인원인지, 특정 직군인지, 일부 계약자의 제시 보수인지 구분해야 합니다. 한 계약자의 보수 또는 공고상 최대치를 프로젝트 전체의 일반 보수로 일반화하면 안 됩니다.

### G. URL과 출처 계층

조사 내용을 최초 보도한 곳이 404 Media라면 **404 Media 원문을 Primary URL**로 두는 것이 적절합니다. TechRepublic, The Decoder 등의 후속 요약은 독립적인 복수 확인으로 계산하면 안 됩니다.

권장 출처 구조:

1. 404 Media 원문
2. 유출 문서 또는 캡처
3. OpenAI의 공식 답변 전문
4. OpenAI Data Controls/Privacy Policy
5. Crossing Hurdles·Mercor의 공식 입장 또는 계약 공고

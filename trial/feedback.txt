검증 기준 시각은 개발자 지침상 **2026-08-27 09:28 KST = 2026-08-27 00:28 UTC**입니다. 초안의 09:27 KST는 작성 시점과 1분 차이일 뿐 본질적인 문제는 아닙니다.

| 항목 | 제시된 공개 시각 | UTC 기준 경과 | 판정 |

| NVIDIA | 8월 26일 16:20 EDT = 20:20 UTC | 약 4시간 8분 | 24시간 내 |

### 메타데이터 수정

항목 4의 다음 조합은 부정확합니다.

```yaml

event_within_24h_window: true
event_within_7d_window: true
```

8월 25일 행사라면 발표 세션의 정확한 시각이 **8월 26일 00:28 UTC 이후**였다는 증거가 없는 한 `event_within_24h_window: true`라고 단정할 수 없습니다. 다만 Category 6이므로 다음처럼 처리하면 됩니다.

```yaml

```

### 명확히 수정해야 할 부분

#### ① “기존 Whisper/Chirp는 false start를 그대로 쓰며 self-correction을 지원하지 않는다”

비교표의 다음 표현은 지나치게 절대적입니다.

> Traditional ASR: Conversational Self-Correction — Not Supported

Whisper 계열을 포함한 ASR은 디스플루언시를 항상 그대로 보존한다고 단정할 수 없습니다. 디코딩, 프롬프트, 후처리 및 서비스 구현에 따라 일부 생략·정규화가 발생할 수 있습니다. 또한 Chirp 3와 모든 Whisper 변형을 하나의 특성으로 묶는 것도 부정확합니다.

권장 표현:

> “Intent-aware correction is generally not exposed as a standardized native feature and often requires separate post-processing.”

#### ② 서로 다른 WER를 직접적인 우열처럼 배열

- 2.6%·4.0%: Artificial Analysis
- 5.04%·5.50%: FLEURS

이는 평가 데이터셋과 조건이 다르므로 한 모델의 대표 WER처럼 혼합하면 안 됩니다. 언어별 평균 방식, 정규화, 스트리밍 지연 조건을 분리해야 합니다.

#### ③ “single end-to-end transformer” 단정

모델 카드가 내부 아키텍처를 명시하지 않았다면 “single end-to-end multimodal transformer”는 분석 또는 추정이지 확인된 사양이 아닙니다. “단일 API 호출로 제공되는 통합 모델”과 “내부적으로 단일 디코딩 패스만 사용한다”는 서로 다른 주장입니다.

### URL 검증

제시된 Google Blog URL은 형식상 가능하지만, 이 URL 하나만으로 API ID, 모델 카드, Gboard 및 macOS 통합까지 모두 입증할 수 없습니다. 모델 카드와 개발자 문서 URL을 별도로 제시해야 합니다.

## 항목 3 — Qwen3.8-Flash / Qwen3.8-Flash-Next

### 판정: **중대한 사실·산술 오류. 전면 재작성 필요**

## 명확한 산술 오류

초안은 다음과 같이 씁니다.

- 125B core
- 51B n-gram table
- 4B MTP
- 총 176B

그러나:

\[
125B + 51B + 4B = 180B
\]

따라서 **176B 총파라미터는 산술적으로 불가능**합니다. 구성 요소 중 하나가 중복 계상되거나 core 수치에 이미 MTP가 포함된 것이라면 그 정의를 명확히 해야 합니다.

### 알려진 Qwen3-Next 구조와의 혼동 정황

초안의 다음 구조는 기존 Qwen3-Next 계열 설명과 매우 유사합니다.

- 48 layers
- Gated DeltaNet와 sparse/full attention의 3:1 비율
- 512 experts
- 10 routed experts + 1 shared expert
- hybrid attention
- MTP

그런데 모델명과 파라미터가 `Qwen3.8-Flash-Next`, 176B/6B로 바뀌어 있습니다. 따라서 공식 기술 보고서가 없다면 기존 Qwen3-Next 아키텍처를 새 모델에 잘못 전사했을 가능성을 배제할 수 없습니다.

특히 Primary URL:

```text
https://github.com/QwenLM/Qwen3.8-Flash-Next
```

은 실제 저장소 존재 여부, 릴리스 태그, README의 공식 모델명, Hugging Face 체크포인트 링크를 확인해야 합니다. GitHub 저장소가 없다면 해당 항목의 핵심 출처가 무효입니다.

### 계층 구조 표가 기술적으로 잘못됨

표는 다음을 “Layer 1~5”처럼 위아래로 쌓인 계층으로 표현합니다.

- MTP
- QSA layers
- GDN layers
- MoE
- n-gram embedding

하지만 이들은 일반적으로 단순한 5단 직렬 레이어가 아닙니다.

- GDN과 attention은 transformer block sequence 안에서 **교차 배치**
- MoE는 각 블록의 FFN 구성 요소
- embedding table은 입력 표현 계층
- MTP는 주 transformer stack 상단의 독립 “Layer 1”이라기보다 보조 예측 헤드

따라서 표 제목을 `Architectural Components`로 바꾸고, 실제 반복 패턴을 별도 도식으로 표현해야 합니다.

### “고정 크기 상태이므로 1M 컨텍스트가 작은 가속기에서 실행된다”는 비약

75%의 레이어가 recurrent/linear attention이어도 나머지 sparse-attention 레이어, MoE weight residency, activation, routing 및 long-context indexing 비용은 남습니다. “smaller accelerator footprints”는 다음 조건이 없으면 입증되지 않습니다.

- 요구 VRAM
- 정밀도
- tensor/pipeline parallel degree
- batch size
- KV 또는 sparse-index 메모리
- 실제 GPU 수

### 처리량 수치의 단위 문제

> 16,000 tokens/sec per GPU  
> 200 tokens/sec per concurrent user

두 수치는 동시 사용자 수, batch size, 입력·출력 길이, quantization 및 speculative decoding 조건이 없으면 비교 불가능합니다. 특히 GB300 NVL72 전체 시스템 결과를 “per GPU”로 환산했다면 선형 환산인지 실측인지 밝혀야 합니다.

### 상태 분류 오류

`Open-Weight Silicon Preview`는 부적절합니다. 이는 실리콘 공개가 아니라 소프트웨어 모델·가중치 공개입니다.

권장:

```text
Official API Release & Open-Weight Model Preview
```

## 항목 4 — AMD MI455X 및 Helios

### 판정: **Category 6 시간 요건은 충족하지만 핵심 사양에 오류**

### 가장 중요한 오류: 메모리 대역폭

AMD가 MI400/MI455X에 대해 공개해 온 대표 수치는 대체로 다음 계열입니다.

- **432GB HBM4**
- 약 **19.6 TB/s per GPU**
- 72 GPU Helios에서 약 **1.4 PB/s aggregate memory bandwidth**
- 약 **31TB aggregate HBM**
- 약 **2.9 EFLOPS FP4**

초안은 이를 다음처럼 적었습니다.

- 23.3 TB/s per GPU
- 1.7 PB/s per rack

산술적으로 23.3 × 72 = 1,677.6 TB/s이므로 초안의 두 값은 서로 일관되지만, **출발점인 23.3 TB/s가 공식 MI455X 사양과 불일치**합니다. 공식 수치 19.6 TB/s를 적용하면:

\[
19.6 \times 72 = 1{,}411.2\ \text{TB/s}
\]

즉 약 **1.41 PB/s**입니다.

따라서 본문, Technical Deep Dive, 비교표, Background Stats의 다음 숫자를 모두 고쳐야 합니다.

| 초안 | 수정 권고 |
|---|---|
| 23.3 TB/s/GPU | 공식 자료의 약 19.6 TB/s/GPU로 확인 |
| 1.7 PB/s/rack | 약 1.4 PB/s/rack |
| MI355X 대비 3배 이상 | 동일 정밀도·동일 단위로 재계산 |

### 공정·패키징 단정

다음 세부 사양은 공식 Hot Chips 슬라이드가 직접 뒷받침하지 않으면 확정적으로 쓰면 안 됩니다.

- N2 compute dies
- N3P cache/I/O chiplets
- compute dies의 copper-to-copper 3D hybrid bonding
- CoWoS-L 세부 연결 방식

AMD가 “2nm/3nm 기반”을 공개한 것과 각 die의 기능을 N2·N3P에 정확히 할당한 것은 다른 수준의 주장입니다. 슬라이드 번호 또는 proceedings 페이지를 붙여야 합니다.

### Helios 구성 수량 누락

“72 MI455X + Venice CPUs + Vulcano 800 NICs”만으로는 랙 토폴로지를 재현할 수 없습니다. 다음 수량을 공식 구성표와 맞춰야 합니다.

- CPU 개수
- GPU tray 수와 tray당 GPU 수
- NIC/DPU 개수
- scale-up switch 수
- scale-out fabric 구성

### `EPYC Venice (96-core)` 재검증

Venice를 단순히 “96-core”로 고정하는 것은 부정확할 가능성이 큽니다. Venice 제품군 전체의 최대 코어 수와 Helios에 탑재되는 특정 SKU의 코어 수는 구분해야 합니다. Hot Chips 발표가 특정 96코어 SKU를 명시한 경우에만 비교표에 유지하십시오.

### SI/PI 설명의 과도한 추론

다음은 발표된 제품 사실이 아니라 작성자의 엔지니어링 추론입니다.

- all-reduce burst가 hybrid-bonded die에서 특정 전압 droop를 유발
- IFoE 때문에 특정 저손실 PCB와 trace-length matching이 필수
- 다음 리비전에서 CPO로 전환

합리적인 분석일 수는 있지만 출처가 없으면 “AMD가 공개한 implementation rules”처럼 쓰면 안 됩니다. 특히 CPO 전환은 로드맵 근거가 필요합니다.

권장 표현:

> “Potential implementation implications include tighter PDN, SI and thermal design constraints; these are analyst inferences rather than disclosed Helios design rules.”

### Hot Chips 날짜

# 3. 요약부의 과장 표현

다음 표현은 증거 수준보다 강합니다.

### “establishes”, “prove”, “validate”

- Google 발표가 음성 인터페이스 전체의 진화를 “확립”
- Qwen 모델 하나가 비용 89% 절감을 “증명”
- AMD 발표가 메모리 월 해결책을 “검증”

벤치마크 조건과 독립 재현이 없다면 다음처럼 낮추는 것이 적절합니다.

- `suggests`
- `demonstrates under reported test conditions`
- `illustrates one approach`
- `company-claimed`

특히 Qwen의 `1/9 training cost`는 비용인지 FLOPs인지 GPU-hours인지 구분해야 합니다. “compute expenditure”는 금전 비용과 계산량을 혼동합니다.

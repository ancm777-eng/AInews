## 3. Kioxia GP1·XL1

### 판정: **제품 발표 원문 미제시 + 서로 다른 제품 사양 혼합 + 정량 오류**

### 명확한 오류

1. **Primary URL이 GP1 또는 XL1 발표 페이지가 아닙니다.**
   - 제시된 URL은 Kioxia의 일반 **XL-FLASH 제품/기술 페이지**입니다.
   - GP1, XL1, FMS 2026 발표, 10M IOPS, 샘플링 일정을 입증하지 못합니다.

2. **두 제품의 사양이 한 줄에 혼합돼 있습니다.**
   - GP1은 PCIe/NVMe SSD로 설명
   - XL1은 CXL 메모리 모듈로 설명
   - 그런데 Technical Deep Dive는 `NVMe 2.2`, `CXL.mem/CXL.io`, `E3.S/E1.S`를 하나의 “Core Technical Specifications”에 묶습니다.
   - **NVMe SSD와 CXL Type-3 메모리 장치는 동일한 프로토콜 제품이 아닙니다.** PCIe PHY를 공유할 수 있어도 NVMe와 CXL.mem은 별도 스택입니다.

3. **“10x IOPS” 계산이 비교표와 맞지 않습니다.**
   - 기준: 1.5M~2.5M IOPS
   - 신제품: 10M IOPS
   - 향상 폭은 약 **4배~6.7배**이지 10배가 아닙니다.
   - 10배라고 하려면 기준 제품이 약 1M IOPS여야 하며 동일 블록 크기·큐 깊이 조건도 맞춰야 합니다.

4. **`CXL-compatible NVMe 2.2 Architecture`는 부정확한 표현입니다.**
   - NVMe 2.2 지원과 CXL.mem 지원은 분리해서 써야 합니다.
   - GP1이 NVMe SSD이고 XL1이 CXL 장치라면 비교표도 두 제품으로 분리해야 합니다.

### 과장 또는 입증되지 않은 주장

- “direct GPU memory extension”
- “HBM tier를 확장”
- “KV cache를 XL-FLASH로 직접 오프로딩”
- “GPU 메모리 직접 접근에 최적화”
- “E3.S와 E1.S 모두 cold-plate liquid cooling 지원”
- “평가 고객 샘플링 H2/Q4 2026”
- “XL1 CXL Memory Module”의 정확한 매체와 메모리 종류
- 512바이트 랜덤 읽기 10M IOPS의 큐 깊이, 워커 수, 소비전력, 지연시간

SSD가 GPUDirect Storage와 같은 경로를 지원하더라도, 곧바로 GPU가 이를 HBM과 동일한 메모리 계층으로 주소 지정한다는 뜻은 아닙니다. 실제 KV 캐시 오프로딩에는 런타임, DMA 경로, 캐시 정책 및 소프트웨어 통합이 필요합니다.

### 시간 검증

FMS 2026 직전 미국 현지 8월 3일 발표라면 24시간 구간에 들어갈 가능성이 높지만, 개별 Business Wire 보도자료의 게시 시각이 필요합니다. 현재의 일반 XL-FLASH URL로는 이벤트 날짜도 확인되지 않습니다.

### 권고 수정

- GP1과 XL1을 별도 표로 분리
- 각 제품의 인터페이스, 매체, 폼팩터, 성능, 샘플링 일정을 각각 기재
- IOPS는 블록 크기뿐 아니라 queue depth, read/write 비율, latency percentile을 함께 표시
- “HBM 대체” 대신 **“소프트웨어가 지원할 경우 저활성 KV 캐시용 하위 저장 계층 후보”** 정도로 완화

## 4. Montage Technology CXL 3.2 MXC

### 판정: **7일 시간 요건은 충족하지만 CXL 기능 설명에 기술 오류**

### 시간 윈도우

- 이벤트 날짜: 2026-07-31
- 7일 기준 시작: 2026-07-28 07:37 KST
- 따라서 `slot_category: 6`에 따른 **7일 예외 범위 안**입니다.
- 이 항목을 24시간 밖이라는 이유만으로 제외해서는 안 됩니다.

다만 이는 학술 연구라기보다 상용 컨트롤러의 시험생산·전시 항목입니다. 슬롯 분류 기준상 허용되더라도, `HW-Circuit-Research`라는 설명과 실제 콘텐츠의 성격은 맞지 않습니다.

### 명확한 기술 오류

1. **CXL 2.0에 메모리 풀링이 없었다는 설명은 틀립니다.**
   - 초안: “CXL 1.1/2.0 controllers … without multi-host memory pooling”
   - CXL 2.0은 스위칭과 메모리 풀링을 도입한 세대입니다.
   - CXL 3.x가 이를 확장했지만, 메모리 풀링 자체가 3.2에서 처음 생긴 것은 아닙니다.

2. **컨트롤러 하나만으로 서버 간 동적 풀링이 구현되는 것처럼 서술했습니다.**
   - Type-3 장치의 CXL.mem/CXL.io 지원만으로 자동으로 여러 서버 노드에 걸친 풀링이 완성되지 않습니다.
   - 다중 호스트 토폴로지, CXL 스위치 또는 fabric, 장치의 multi-headed 지원, 시스템 펌웨어와 OS 메모리 관리가 필요합니다.

3. **`sub-nanosecond controller latency`는 출처 없는 과도한 수치입니다.**
   - 외부 CXL 링크 전체 지연시간과 컨트롤러 내부 추가 지연을 구분하지 않았습니다.
   - 이 수치를 유지하려면 측정 지점, 공정, 패킷 조건 및 공식 데이터시트가 반드시 필요합니다.

4. **“full CXL 3.2 fabric switching”을 MXC 단일 칩의 기능으로 단정할 수 없습니다.**
   - 메모리 확장 컨트롤러와 CXL 스위치는 역할이 다릅니다.
   - 컨트롤러가 3.2 호환 Type-3 장치라는 사실만으로 완전한 fabric switching 기능을 보유한다고 볼 수 없습니다.

### 맞는 기술 요소

- PCIe 6.0의 링크 속도를 **64 GT/s per lane**으로 표기한 것은 맞습니다.
- CXL Type-3 메모리 장치가 일반적으로 CXL.io와 CXL.mem을 사용하는 설명도 타당합니다.
- 외장 CXL 메모리가 로컬 DDR보다 높은 지연시간을 가질 수 있다는 Critical View도 방향상 맞습니다.

### 출처 문제

`https://www.montage-tech.com/News/Press_Releases`는 보도자료 목록일 뿐 해당 발표의 고유 URL이 아닙니다. 다음을 입증할 개별 발표문이 필요합니다.

- 제품의 정확한 명칭
- CXL 3.2 준수 범위
- 시험생산일
- “industry-first”의 비교 기준
- FMS/CXL Mini DevCon 시연
- 샘플링 일정
- 지원 DDR 세대·채널 수·용량·호스트 수
- 컨트롤러 지연시간

### 권고 수정

“CXL 3.2가 메모리 풀링을 처음 가능하게 했다”가 아니라 다음처럼 써야 합니다.

> CXL 2.0에서 도입된 스위칭·메모리 풀링을 PCIe 6.0 기반 CXL 3.x 환경으로 확장하며, 실제 다중 호스트 풀링에는 별도 CXL 스위치와 시스템 소프트웨어 지원이 필요하다.

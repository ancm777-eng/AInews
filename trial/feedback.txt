## 종합 판정

초안은 **시간 윈도우 판정 3건이 증빙 부족**이며, 본문에는 몇 가지 **명확한 수치·기술적 모순**이 있습니다. 특히 다음 사항은 수정이 필요합니다.

1. **Item 1·2:** `2026-07-28`이라는 날짜만으로는 24시간 내 사건이라고 확정할 수 없습니다.
2. **Item 1:** 총사업비·출자·차입금 숫자가 서로 맞지 않으며, `80% 지분 이전 = 부채 80% 이전`으로 해석한 부분도 부정확합니다.
3. **Item 2:** “차원 절반 → 비트 보안성 절반 → 키 크기 두 배”라는 결론은 수학적으로 자동 성립하지 않습니다. “AES-128이 수학적으로 안전하다”는 표현도 과도합니다.
4. **Item 3:** `did:key` 자체에는 기본적인 폐기·키 회전 기능이 없으므로 “one-click revocation”을 DID 기능처럼 기술하면 안 됩니다.
5. **Item 4:** `120×120 mm = 8× reticle size`는 표준 26×33 mm 노광 필드의 **면적 기준으로 계산하면 약 16.8배**라서 정의가 필요합니다. EMIB-T의 TSV를 “직접 후면 전력 공급”으로 단정한 것도 과도합니다.
6. **행사 일정:** DAC 2026을 `7월 29~31일`로 기재한 일정은 본문의 “concluding tracks” 설명과도 맞지 않으며, 공식 일정 재확인이 필요합니다.

### 명확한 재무 수치 모순

제시된 숫자는 다음과 같습니다.

- BlackRock 현금 출자: **$4.9B**
- 프로젝트 채권 부채: **$12.5B**
- Meta 현물 출자: **$2.3B**
- Meta가 받은 현금 분배: **$1.0B**
- 주장된 총사업비: **$14B**

Meta의 순출자를 `2.3 - 1.0 = $1.3B`로 보면:

- 순자본 출자: `4.9 + 1.3 = $6.2B`
- 여기에 부채 $12.5B를 더하면: **$18.7B**

즉, 본문의 모든 금액을 동일 프로젝트의 자금조달 원천으로 보면 **$14B와 맞지 않습니다**. 반대로 $14B가 평가가치나 특정 단계의 시설비라면, $12.5B 채권이 전체 프로젝트 부채인지 리파이낸싱 금액인지 등을 별도로 설명해야 합니다.

지분 비율 자체는 순출자 기준으로는 대략 맞습니다.

- BlackRock: `4.9 / 6.2 ≈ 79%`
- Meta: `1.3 / 6.2 ≈ 21%`

따라서 **80/20 지분 구조는 가능하지만, 총사업비 및 부채와의 관계는 현재 서술로는 모순**입니다.

### 회계·법률 표현 오류

다음 문장은 부정확합니다.

**80% 지분 보유와 프로젝트 부채의 80% 부담은 같은 개념이 아닙니다.** 프로젝트 법인이 차입자이고 비소구 또는 제한소구 구조라면, 지분율과 부채 부담은 별도로 설명해야 합니다.

또한 “off-balance-sheet” 여부는 80%를 외부에 매각했다고 자동 확정되지 않습니다. Meta가 다음 중 하나에 해당하면 연결 또는 리스부채 인식 문제가 남습니다.

- 실질적 지배력 보유
- 유일한 임차인으로서 자산 사용을 통제
- 확정 구매·갱신 약정
- 잔존가치 보증
- 변동이익에 대한 실질적 노출

따라서 공식 회계 공시가 없다면 **“off-balance-sheet” 대신 “potentially deconsolidated/project-finance structure”** 정도로 낮춰 써야 합니다.

## 2. Anthropic Claude Mythos / HAWK / reduced AES

### 판정: **시간 미입증 + 암호학적 결론 과장**

### 시간 검증

Item 1과 동일하게 `2026-07-28` 날짜만으로는 24시간 내 사건인지 판단할 수 없습니다. 해당 날짜 중 윈도우에 포함되는 UTC 구간은 **22:35~23:59 UTC**뿐입니다. 미국 현지 시간 기준 발표였다면 포함될 수도 있지만, 원문 시각이 필요합니다.

따라서 `event_within_24h_window: true`는 현재 메타데이터만으로 입증되지 않습니다.

### HAWK 관련 논리적 비약

다음 연쇄 결론은 자동으로 성립하지 않습니다.

> lattice dimension halved → effective key strength halved → key sizes must double

격자 문제의 공격 복잡도는 다음에 따라 달라집니다.

- 격자 차원
- BKZ 블록 크기와 비용 모델
- root-Hermite factor
- classical/quantum sieve 가정
- 키 복구 성공 확률
- 대상 파라미터 세트

따라서 “차원이 절반으로 감소했다”는 사실만으로 **비트 보안성이 정확히 절반**이라고 할 수 없고, 키 크기를 **정확히 두 배로 해야 한다**고도 단정할 수 없습니다. 기술 논문에 파라미터별 security estimate가 있다면 그 값을 직접 인용해야 합니다.

또한 HAWK를 단순히 “Module Lattice Isomorphism Problem 기반”이라고 요약하는 것이 원 논문의 정확한 문제 정식화인지 확인해야 합니다. HAWK의 설계 기반과 새 공격의 환원 대상 문제를 구분해 써야 합니다.

### AES 표현 오류

다음 표현은 수정해야 합니다.

> full 10-round AES remains mathematically secure

AES-128의 절대적·수학적 안전성이 증명된 것은 아닙니다. 적절한 표현은 다음과 같습니다.

> 현재 공개된 연구 기준으로 full-round AES-128에 대한 실용적인 키 복구 공격은 알려져 있지 않다.

7-round reduced AES에 대한 공격 개선은 중요한 연구 결과일 수 있으나, 이를 곧바로 운영 환경의 AES-128 위험으로 연결하면 안 됩니다.

### 속도 향상 수치의 기준 불명확

`200×–800× speedup`에는 최소한 다음 조건이 필요합니다.

- 비교 대상 논문 또는 기존 공격
- time complexity 변화인지 실제 wall-clock인지
- 데이터·메모리 복잡도
- CPU/GPU 및 병렬화 조건
- 200배와 800배가 각각 어떤 파라미터에서 나온 값인지

복잡도식의 상수항 또는 guessing factor 제거를 실제 실행시간 배수로 표현했다면 과장될 수 있습니다.

### 모델·비용·심사 상태

다음 항목은 1차 자료에서 명시적으로 확인되어야 합니다.

- 공식 모델명: **Claude Mythos Preview**
- `Möbius Bridge`가 논문상의 정식 공격명인지
- `$100,000`이 실제 API 청구액인지, 내부 연산비용 환산값인지
- Apache-2.0이 코드에만 적용되는지 논문·데이터에도 적용되는지
- “peer-reviewed”가 학회·저널 심사를 통과했다는 의미인지

비공개 내부 모델을 사용했다면 “API compute cost”라는 표현은 모순 가능성이 있습니다. 외부 API 사용이 아니라면 **estimated compute cost**라고 써야 합니다.

### 과장된 비교

> outpace years of expert human cryptographic review

단일 결과만으로 일반화하기 어렵습니다. 연구자 유도 60시간, 문제 선택, 검증, 기존 문헌 제공 여부가 개입되었다면 “autonomous”보다 **researcher-guided AI-assisted cryptanalysis**가 적절할 수 있습니다.

### 권고 판정

- `event_within_24h_window`: **unverified**
- “보안성 절반·키 크기 두 배”: **원 논문의 구체적 추정치가 없으면 삭제**
- “mathematically secure”: **오류, 수정 필요**
- 상태: 학회·저널 정보가 없다면 `Peer-Reviewed` 대신 `Corporate Research Disclosure`

- 기본적인 키 회전·DID 폐기 메커니즘이 없음

따라서 다음 서술은 부정확합니다.

> Identity Verification (`did:key`) … One-Click Revocation

폐기 기능은 별도 credential status list, issuer registry, denylist, delegation token 만료, 게이트웨이 정책 등으로 구현될 수 있지만 **`did:key` 자체가 즉시 폐기를 제공하는 것은 아닙니다.** 어떤 레이어가 폐기를 담당하는지 분리해서 써야 합니다.

### 과도한 기능 주장

다음도 사양 문서에서 직접 확인해야 합니다.

- 모든 agent request마다 서명된 delegation credential을 첨부하는지
- MCP 자체를 “확장”하는지, MCP 위에 별도 인증 계층을 제공하는지
- “tamper-proof”인지, 보다 정확히는 “tamper-evident”인지
- v1.0.0이 최종 표준인지, 초기 공개 사양 또는 community draft인지
- DIF가 공동 출시 주체인지, 단순 작업반 호스팅·거버넌스 인수 주체인지

감사 로그는 암호학적 서명만으로 삭제 방지까지 보장하지 않으므로 **tamper-proof보다 tamper-evident**가 안전한 표현입니다.

## 4. Cadence / Synopsys / Intel Foundry

### 판정: **7일 예외 충족; reticle 배수와 EMIB-T 전력 설명 수정 필요**

### 시간 검증

이 항목은 `slot_category: 6`이고 `event_within_7d_window: true`이므로 일반 24시간 규칙을 적용할 필요가 없습니다.

- 이벤트 날짜: **2026-07-29**
- 기준 날짜: **2026-07-30**
- 7일 내 조건: **충족**

따라서 시간상 stale로 지적할 사안은 없습니다.

### `120×120 mm = 8× reticle` 문제

본문은 일반적인 reticle exposure field를 약 `858 mm²`라고 설명합니다.

- 표준 필드: `26 × 33 mm = 858 mm²`
- 패키지: `120 × 120 mm = 14,400 mm²`
- 면적비: `14,400 / 858 ≈ 16.8`

따라서 **패키지 외곽 면적을 기준으로 하면 8배가 아니라 약 16.8배**입니다.

`8× reticle`이 다음 중 하나를 뜻할 수는 있습니다.

- 실제 silicon-interposer 면적
- 패키지 내부에서 사용 가능한 active area
- 업계의 특정 interposer-size 등급
- reticle stitching으로 구현한 유효 영역

그러나 그 경우 `120×120 mm package size`와 `8× reticle silicon area`를 동일한 값처럼 병기하면 안 됩니다. **패키지 외형과 인터포저/브리지의 유효 실리콘 면적을 분리**해야 합니다.

### EMIB-T 설명 과장

EMIB-T의 TSV는 브리지의 수직 연결을 제공할 수 있지만, 이것을 곧바로 다음과 같이 표현하는 것은 과도합니다.

> direct backside power delivery  
> reduced vertical IR voltage drop via direct TSVs

후면 전력 공급은 die-level backside power delivery network와 패키지 브리지 TSV를 구분해야 합니다. Intel 18A의 PowerVia와 EMIB-T의 TSV 기능도 동일하지 않습니다. 공식 문서가 전력 공급 경로를 명시하지 않았다면 다음처럼 낮춰 쓰는 편이 정확합니다.

> EMIB-T adds vertical connectivity through TSV-equipped embedded bridges, potentially improving routing and power-delivery integration depending on the package implementation.

### EDA 도구 분류 보완

초안은 Cadence의 `Allegro and Virtuoso multiphysics stacks`라고 표현했지만, 실제 인증 도구는 기능별 제품명을 분리해야 합니다. 예를 들어:

- 디지털 구현
- custom/analog design
- package/substrate design
- SI/PI 분석
- thermal analysis
- 3D-IC system planning

Synopsys도 `3DIC Compiler` 하나가 모든 물리해석을 직접 수행한다고 단순화하지 말고, 연동되는 분석·signoff 도구를 기재해야 합니다.

### 근거 없는 기능 확대 가능성

다음은 인증 발표에 명시되지 않았다면 삭제하거나 별도 전망으로 구분해야 합니다.

- 최대 **12개 HBM4/HBM4e** 스택
- HBM4e 공식 지원
- `12× reticle by 2028`
- 모든 툴에서 `SI/PI/thermal/EM`을 단일 환경으로 완전 통합
- 전 세계에서 즉시 사용 가능한 14A production-ready flow

특히 `Intel 14A PDK v0.5`는 통상 초기 개발 단계 의미가 강하므로, 이를 18A-P PDK 1.0과 같은 수준의 “certification complete”로 묶으면 성숙도를 과장할 수 있습니다.

### 노드 표현

Intel 18A·14A를 “sub-2nm”로 분류하는 업계 관행은 가능하지만, 숫자가 실제 게이트 길이나 물리적 치수라는 의미는 아닙니다. 다음 주석을 권합니다.

> Node names are commercial process labels and do not denote a literal measured feature size.

### 권고 판정

- 7일 시간 조건: **통과**
- `120×120 mm = 8× reticle`: **정의 없는 상태에서는 수치 불일치**
- EMIB-T 직접 후면 전력 공급: **공식 자료 없으면 삭제 또는 완화**
- 14A PDK 0.5: **초기 enablement와 production certification을 구분**

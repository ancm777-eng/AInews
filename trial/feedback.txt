## 1. Wave Forcing / WaveRT

**판정: 주제 교체 근거는 없으나, 성능·경제성 해석을 수정해야 합니다.**

### 초안 자체로 확인되는 문제

- **7배 확장이라는 산술은 맞습니다.**  
  `134.8 ÷ 19.06 ≈ 7.07배`입니다.

- 그러나 **GPU 8개로 약 7.07배의 처리량을 얻었다는 결과가 프레임당 비용 절감을 입증하지는 않습니다.** 동일한 GPU·가격·측정 조건을 가정하면:
  - 병렬 효율: 약 **88.4%**
  - 프레임당 GPU 사용시간: 단일 GPU 대비 약 **13.1% 증가**

  따라서 “프레임당 서비스 비용을 대폭 낮춘다”는 문장은 이 수치만으로 뒷받침되지 않습니다. 단일 GPU에서의 알고리즘 개선 효과와 다중 GPU 확장 효과를 분리해야 합니다.

- **처리량과 응답 지연시간을 혼동하고 있습니다.** 134.8 FPS는 지속 출력 처리량이지, 첫 프레임 도착시간이나 입력 변경에 대한 반응시간이 아닙니다. “instantaneous”, “speed-of-light”, “기존 방식에서는 수학적으로 불가능”은 삭제하거나 완화하는 편이 정확합니다.

### 원문 확인이 필요한 주장

- arXiv `2611.00859`의 실제 제목·저자·소속
- Wave Forcing과 WaveRT의 공식 명칭 및 공개일
- `SJTU-DENG-Lab/WaveForcing-1.3B`의 실제 공개 여부
- Apache-2.0이 코드에만 적용되는지, 가중치에도 적용되는지
- H200 8개, Wan2.1-T2V-1.3B, 134.8 FPS의 해상도·배치·VAE 포함 여부
- 비교표의 “기존 방식 25 FPS 미만”, “Rolling Forcing 40~60 FPS”의 실측 출처

**권장 수정:** 제목은 “8×H200에서 134.8 FPS 처리량 보고”처럼 측정 조건을 드러내고, 지연시간·품질·비용은 별도 지표로 기술하십시오.

## 2. Agentic Computer Graphics

**판정: 유효한 연구·창작 도구 주제이지만, 서베이·분류체계와 구현·벤치마크 공개를 구분해야 합니다.**

이미지·디자인·그래픽스 에이전트는 이번 브리핑의 유효한 주제입니다. 하드웨어 중심 기사가 아니라는 이유로 교체할 필요는 없습니다.

### 보완할 핵심

- **분류체계 제안과 표준 확립은 다릅니다.** 논문이 taxonomy를 제시했다면 “표준화된 프레임워크를 확립했다”보다 “분류체계와 개념적 실행 구조를 제안했다”가 적절합니다.
- **서베이 작성 도구와 배포 가능한 그래픽스 에이전트는 다릅니다.** 문헌 탐색에 에이전트를 사용했다는 사실만으로 공개 실행 프레임워크나 벤치마크를 제공했다고 표현하면 안 됩니다.
- “세 가지 필수 기둥”, “수백 개 파이프라인 교차 평가”, “공개 분석 harness”, “system architecture benchmark”는 각각 원문의 정의·방법론·공개 산출물로 확인해야 합니다.
- 생성 모델을 모두 “편집 불가능한 평면 비트맵 출력”으로 묶는 설명은 지나치게 포괄적입니다. **“다수의 래스터 이미지 생성 시스템은 편집 가능한 절차적 구조를 직접 제공하지 않는다”** 정도로 한정하십시오.
- Adobe의 라이선스 경쟁력 약화는 가능한 전망이지, 이 논문이 검증한 결과가 아닙니다.

### 원문 확인이 필요한 주장

arXiv `2611.01860`의 제목·전체 저자·소속과 함께, **UT Austin·Stanford·UC Berkeley의 참여**, Maneesh Agrawala·Leonidas Guibas의 실제 저자 참여를 확인해야 합니다. 공동 저자 소속이 있다는 것만으로 “해당 대학들이 주도한 컨소시엄”이라고 단정할 수는 없습니다.

## 3. Yandex FLAMIA

**판정: 시간 윈도우상 유효합니다. 가속 범위와 전체 학습 효과를 구분해야 합니다.**

### 초안 자체로 확인되는 문제

- **성능 범위가 본문 안에서 일치하지 않습니다.**
  - Overview: **1.10~1.42배**
  - Technical Deep Dive: B300에서 **1.06~1.42배**

  두 하드웨어 결과를 합쳐 설명한다면 전체 범위는 **1.06~1.42배**입니다. 원문에서 특정 조건을 제외한 범위라면 그 조건을 명시해야 합니다.

- **attention 커널 가속을 전체 학습 비용 절감으로 직접 환산하면 안 됩니다.**  
  1.10~1.42배 가속은 해당 연산 시간으로는 약 **9.1~29.6% 감소**에 해당하며, 전체 학습 개선은 attention의 실행시간 비중에 좌우됩니다.

- “zero loss degradation”은 검증 범위를 과도하게 넓힐 수 있습니다. **어떤 모델 규모·학습 토큰 수·평가지표에서 유의한 악화가 관찰되지 않았는지**를 기재해야 합니다.
- 메모리 사용량 감소만으로 **열·전력 피크 감소**가 입증되지는 않습니다. 전력 측정이 없다면 가능성으로 표현하십시오.

### 원문 확인이 필요한 주장

- arXiv `2611.03344`와 FLAMIA의 대응 관계
- Yandex Research 소속 및 공식 약어 풀이
- `yandex-research/flamia-blackwell-attention`의 존재·라이선스·포크 관계
- B200/B300별 수치와 실제 비교 대상
- causal safety에서 문서 경계 격리와 **같은 문서 내 미래 토큰 누출 방지**를 각각 어떻게 보장하는지

비교표의 “표준 블록 양자화는 누출 위험이 높다”는 표현도 특정 구현의 문제인지 일반적 한계인지 구분해야 합니다.

## 4. NVIDIA Attribution

**판정: 7일 예외로 유지 가능하지만, 시간 메타데이터와 진단 범위 설명을 수정해야 합니다.**

### 확인되는 시간 오류

`event_date: 2026-11-02`와 `event_within_24h_window: true`는 양립하지 않습니다. 다음처럼 수정하십시오.

```text
event_within_24h_window: false
event_within_7d_window: true
```

지침상 `slot_category: 6`의 7일 예외가 적용되므로, 이 문제만으로 기사 교체를 요구하지는 않습니다.

### 사실 검증의 핵심

- **XID 149의 공식 정의**를 NVIDIA Xid 문서와 대조해야 합니다. 초안은 이를 “고속 SerDes 신호 무결성 문제”, “물리적 NVLink 열화”, “특정 포트 식별”로 연결하지만, 이 세 주장은 동일하지 않습니다.
- 오류 코드가 링크 관련 오류를 나타내더라도 그것만으로 **PCB·커넥터·전기적 신호 열화가 확정되는 것은 아닙니다.** 원문이 어떤 텔레메트리와 규칙을 추가로 사용하는지 확인해야 합니다.
- “수십만 GPU”, “주당 수백만 워크로드”, Slurm·Kueue 지원, REST Service·Blueprint 구조, `dsx-ai-factory/attribution` 저장소는 각각 공식 출처가 필요합니다.
- “NVIDIA Workload Recovery가 실험 단계”라는 서술도 별도 제품 문서로 확인해야 합니다.
- 결정론적 규칙 엔진이라는 사실은 **결과 재현성**을 설명할 수 있지만, 진단 정확성까지 보장하지는 않습니다.

**권장 수정:** 물리적 고장 원인을 확정한다는 표현보다 “하드웨어 오류 신호와 분산 작업 실패를 연계해 원인 후보 노드를 식별한다”는 수준에서, 공식 문서가 입증한 범위만 기술하십시오.

## 요약·행사 일정 보완

### 종합 전망
- 네 사건을 묶은 “coordinated push”는 공동 행동의 근거가 없다면 **“서로 다른 연구·제품에서 공통된 흐름이 관찰됐다”**로 바꾸십시오.
- “병목이 FLOPs에서 인터커넥트로 이동했다”는 결론은 너무 일반적입니다. **워크로드·병렬화 방식에 따라 통신과 신뢰성의 중요성이 커진다**고 한정하는 것이 타당합니다.
- 첫 프레임 지연시간 자료 없이 Wave Forcing을 “sub-second interactive generation”과 연결하지 마십시오.

### 행사 일정
SC26·NeurIPS 2026·IEDM 2026·DesignCon 2027의 날짜는 **현재 답변에서 공식 일정과 대조하지 못했습니다.** 발행 전에 공식 페이지로 확인하고, 본 행사·튜토리얼·전시 일정을 구분해야 합니다. “예상 세션 주제”도 확정 프로그램과 분리하십시오.
